# The mutation ratchet's baseline. See build-logic/src/main/kotlin/soulbind.mutation.gradle.kts.
#
# WHAT THIS IS. One row per module: the number of mutants PIT generated, how
# many a test killed, how many a test ran without noticing, and how many no test
# executed at all. `mutationRatchet` fails a module whose SURVIVED or NO_COVERAGE
# count is higher than its row here.
#
# WHY A RATCHET AND NOT A THRESHOLD. A threshold is a number somebody negotiates
# the first time it is inconvenient, and a lowered threshold is a decision about
# what this project permanently stops noticing. A ratchet asks only "is this
# worse than it was". Nobody has to defend a number and nobody can drift past
# one.
#
# RAISING A ROW IS A DELIBERATE ACT, in the same commit as the change that
# needed it, with the reason in the commit message -- exactly like re-pinning an
# artefact in a pins.env. A row edited on its own, in its own commit, is the
# smell this file exists to make visible.
#
# NEW UNTESTED CODE RAISING NO_COVERAGE IS NOT AN EXCEPTION. It is the case this
# file exists for.
#
# TIMED_OUT IS A KILL, and it has its own column because it is the one status
# that moves on its own: a mutant near PIT's timeout budget lands in TIMED_OUT
# on a loaded machine and in SURVIVED on an idle one. If this guard fires and
# the only movement is between those two columns, it is timing noise -- re-run
# that module alone before changing anything. There is deliberately NO
# tolerance for it: a tolerance is a threshold by another name, and the whole
# argument for a ratchet is that nobody negotiates a number.
#
# ONE TABLE, and that is MEASURED rather than assumed. These rows were keyed by
# environment for one release, on the reasoning that a reaper session has a
# MariaDB server and the workstation does not. A session run emitted its own
# rows and every one matched these exactly, `core` included -- because the
# session stage deliberately runs the ratchet WITHOUT MariaDB in scope, which is
# stated in .reaper.toml at the invocation. Two identical tables drift, and
# drift makes the guard protect less without saying so.
#
# WHEN A ROW MOVES, DIFF THE MUTANT IDENTITIES, NOT THE COUNTS. Counts say
# something changed; only identities say what, and the answer has twice been
# "one method, and nothing else in the module". Three runs of an unchanged tree
# gave `core` 47, 43 and 46 survivors with TIMED_OUT at 7, 7 and 10 -- so not
# the timing noise described above -- and every mutant that moved was in
# Storage.open, whose decisions were then only observable through a race. The
# fix was a seam, not a number: a row raised to the worst observed value buys
# stability by making the guard blind. DECISIONS 10.46.
#
# ONE FIXED CONFIGURATION is what keeps that true: the fuzz tier excluded, no
# MariaDB, one Gradle command in the manifest. Change any of those and the
# numbers move for a reason that is not a regression.
#
# NOT TOML, deliberately, though this repository's convention is TOML wherever
# it owns the file. This is not configuration -- it is a checked-in expectations
# table, closer to a lock file, and it is laid out in columns because the thing
# that matters about it is being readable in a diff. Reading it also needs no
# parser, and build-logic ships no dependencies.
#
# Recorded 2026-08-21, after DECISIONS 10.28 and 10.29. The `core` row was
# re-measured 2026-08-23 after 10.46, and set from three consecutive runs whose
# survivor sets were identical -- not from one sample, which is what produced
# the wrong answer the first three times. `core` and `protocol` moved again
# for 10.47, which added the gate-description path: both rows are TIGHTENED
# rather than raised, because the new code arrived covered and took two
# survivors and a no-coverage row with it.
#
# ALL FIVE ROWS TOUCHED BY MEASURES were re-measured 2026-09-09, after the
# battery refused the change. Every row moved for a reason, and the reasons are
# not the same:
#
#   policy, protocol   TIGHTENED back to their old survivor and no-coverage
#                      counts. The new code arrived covered; the mutants the
#                      battery caught were killed rather than recorded.
#   config             no-coverage 2 -> 3. The one addition is unreachable BY
#                      CONSTRUCTION: fromTable's TABLE_ARRAY branch throws, and
#                      ConfigKey refuses a nested table array at declaration, so
#                      no input reaches it. The switch must still be exhaustive.
#                      (This row had ALSO been silently red since 8a13aaa, which
#                      shipped the table-array type without re-measuring. The
#                      battery is what said so; those mutants are killed here,
#                      not recorded.)
#   connector-plan     no-coverage 7 -> 13. Velocity plugin wiring and the
#                      adapter over the host's query API: reachable only with a
#                      running proxy and a running dashboard. The SQL itself is
#                      NOT in this number -- it was separated behind a seam and
#                      is now tested against a fake statement, which took 31
#                      no-coverage mutants down to these 13.
#   core               survivors 39 -> 44, no-coverage 113 -> 119.
#                      FOUR of the five new survivors are `setNull` calls that
#                      bind a rule's absent measure columns. SQLite cannot
#                      distinguish an unset parameter from a null one, so they
#                      are unkillable in THIS configuration and would be killed
#                      on MariaDB -- which this table deliberately excludes. The
#                      fifth is an equivalent tie-break, reasoned about at the
#                      line in GateEvaluator.strongestByName. The no-coverage
#                      additions are the measure repository's insert-race probe,
#                      the same shape as the runtime-config one beside it.
#
# `connector-plan` TIGHTENED 2026-09-10: no-coverage 13 -> 12, BELOW where it
# stood before the activity-index change. It got there the wrong way round.
#
# 3b491fa shipped without re-measuring this module -- hand-checking five mutants
# is not the same as running the ratchet -- and it took no-coverage to 14. The
# battery caught it, which is what the battery is for.
#
# The addition was `HostQueries.activityIndex`: the old adapter computed
# playtime in SQL and needed only `query`, where the new one calls the host's
# index as a second method. Raising the row would have been easy and wrong. The
# reasoning behind the original 13 -- "this needs a running dashboard" -- was
# only half true: the `QueryService.getInstance()` lookup needs one, the three
# lines of forwarding around it do not, and the host's API is two interfaces
# that a proxy can stand in for. Splitting `live()` from `of(service)` made the
# forwarding testable and killed two mutants that had been sitting in this
# column since the row was written, including one that returns zero from the
# activity index -- which is every player below every threshold.

# `connector-velocity` MOVED 2026-09-10, for the message templates: total
# 214 -> 235, killed 164 -> 183, no-coverage 47 -> 49. Survivors held at 3,
# which is the number that matters -- twenty-one new mutants arrived and
# nineteen are killed.
#
# The two additions are ONE branch: the catch in `Messages.render`. MiniMessage
# is lenient, and that was probed rather than assumed -- eighteen malformed
# templates, none of which threw, and the test `typoIsShownNotSwallowed` pins
# that behaviour so the day a version starts throwing is a red test and not a
# surprise. So no template reaches the catch. It stays because render runs on a
# command thread and on the join event thread, where an escaping exception costs
# a player their message or their connection.
#
# TWO OTHERS were caught by this guard and are NOT recorded here: `playersOnly`
# and `unavailable` had no test at all, because the only caller is the plugin
# class no test constructs. They are killed rather than baselined.

# `core` survivors read 44 on two consecutive runs while TIMED_OUT moved 9 -> 8,

# across both, so 44 is measured rather than sampled once.
